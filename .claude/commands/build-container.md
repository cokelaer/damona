# Workflow: Apptainer Factory

Build a Damona container for: **$ARGUMENTS**

## Step 0 — Triage (orchestrator, no agent)

Classify the software before spawning anything:

- **SIMPLE** — single tool (or few binaries), C/C++/Rust/Go source or prebuilt Linux binary, light deps (zlib-class). Examples: seqtk, mash, kmc, minigraph.
- **COMPLEX** — conda/micromamba stack, Python/R/Perl runtime, many binaries, heavy libs (hdf5, boost). Examples: hicexplorer, bakta, repeatmasker.

SIMPLE → **fast path** (Step 1F). COMPLEX → **full pipeline** (Steps 1–3). When unsure, pick fast path; a QA FAIL escalates to full pipeline.

## Step 1F — Fast path (recipe-architect only, then QA)

Call `recipe-architect` once with the requirements AND instruct it to:
1. Design the recipe (timeboxed research, see agent rules). Pin every input and assert the
   version in `%test` — "simple tool" is not a reason to skip it; the unpinned recipes that
   went wrong in the registry (fastp, gffread, mafft, bamqc) were all simple tools.
2. Build it itself with `damona build` (it has Bash). Run the build FROM the recipe's directory (`damona/software/<name>/`) — `damona build` writes the `.img` to the cwd, and it belongs next to the recipe.
3. Report `.img` path + build log tail + Goal State.

Then go straight to Step 3 (QA). Skip build-engineer entirely.

## Step 1 — Design (recipe-architect) [COMPLEX only]

Call the `recipe-architect` agent with the user requirements above.
- Generate `Singularity.NAME_X.Y.Z` recipe in the project source.
- Validate the base image is reachable.
- **Pin every input** (package versions, download URLs, git tag or commit, subproject wraps,
  base-image tag) and assert the version in `%test`. See the agent's Version Pinning section.
  An unpinned recipe produces a container whose key stops being true on the next rebuild, and
  the deposit that goes to Zenodo is permanent.
- Output: recipe file path + Goal State.

## Step 2 — Build (build-engineer) [COMPLEX only]

Call the `build-engineer` agent with the recipe from Step 1.
- Run `damona build <recipe>` FROM the recipe's directory (`.img` is written to cwd; it belongs next to the recipe).
- Produces `NAME_X.Y.Z.img`, not `.sif`.
- Capture stdout/stderr. Build only — NO functional testing (recipe `%test` runs at build time; deeper checks are QA's job).
- Output: `.img` path + build log.

## Step 3 — Verify (qa-specialist) — always runs

Call the `qa-specialist` agent with the `.img`, the recipe path, the build log, and the Goal State.
- `apptainer inspect`, binary checks, manual tool run, bash + Zenodo cleanliness.
- Verify via `apptainer exec`, not only `apptainer run` — Damona wrappers use `exec` and bypass the `%runscript`, so anything set only there is untested.
- Test the HPC case explicitly: read-only / absent `$HOME` (`--contain --no-home`). Tools that silently degrade (catching export exceptions and logging a warning) pass a naive check while producing no output.
- Note the wall time of a realistic run and report it. A correct container that is too slow to use gets abandoned, so a PASS verdict on correctness alone is not the whole story.
- Check the version the binary reports against the recipe name and the key that will go into
  `registry.yaml`, and audit the recipe for unpinned inputs. Both go in the report.
- Output: Test Pass Report (PASS/FAIL).

## Step 4 — Handover (orchestrator)

**On FAIL:** loop back to `recipe-architect` with the error log for a self-correction cycle (fast-path failures escalate to the full pipeline).

**On PASS**, the orchestrator finishes the recipe-add work itself — no agent owns this, do NOT skip it:

1. **registry.yaml** — add placeholder release entry in `damona/software/<name>/registry.yaml`:
   - `binaries:` lives at **software level** (space-separated), NOT inside the release.
   - Release entry fields: `download` (`https://zenodo.org/record/XXXXXXX/files/<name>_X.Y.Z.img`), `md5sum: XXXXXXX`, `doi: 10.5281/zenodo.XXXXXXX`, `filesize: XXXXXXX`. Keep `XXXXXXX` until the image is uploaded to Zenodo.
   - Match field layout of a recently added software (e.g. foldseek) if in doubt.
2. Do NOT edit the global `damona/software/registry.yaml` (auto-generated by pre-commit hook).
3. Report to the user: `.img` path, size, QA verdict, the version the binary reports, and the
   remaining manual step (Zenodo upload → fill placeholders). If QA listed unpinned inputs, say
   so here — after publication the deposit is immutable and the only remedy left is a
   `mislabelled:` flag.
4. **Warn the user that the placeholder is now live.** Both pre-commit hooks match `damona/software/.+/registry\.yaml$` but run with `pass_filenames: false`, so they rescan every software dir. The *next* commit touching any registry.yaml — including an unrelated one from another session or terminal — bakes this software into the committed global `registry.yaml` (with `record/XXXXXXX` URLs) and bumps the README.rst counts. Until Zenodo publication, the placeholder is a commit away from being published.

## Step 5 — Removal (orchestrator) — if a recipe is abandoned or deleted

`rm -rf damona/software/<name>/` is **not sufficient**; the placeholder may already be in committed generated files (Step 4.4). Always:

1. `python damona/software/update_global_registry.py` and `python .pre-commit-hooks/update_readme.py`
2. Verify `grep -ci <name> damona/software/registry.yaml` returns `0`
3. Check `git log` for commits made while the placeholder existed — the leak arrives via *someone else's* commit, so a clean `git status` before deleting proves nothing
4. Commit the regenerated files

Deleting a `.img` or a recipe directory is irreversible: confirm scope with the user first, and read any file in that directory you did not create (hook-generated `README.md`, stray run logs) before removing it.

**Zenodo publication is the USER's job — never run `damona publish` (or any Zenodo upload) yourself, even if asked "is it on Zenodo?" or if it seems like the natural next step. Stop after the registry placeholder and hand over.**

Communication rules: handoffs include file path + goal state; build failures pass the last 20 log lines back; never guess a dependency version (search, timeboxed); a QA FAIL is a veto.
